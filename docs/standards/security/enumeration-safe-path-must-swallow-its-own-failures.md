# On an enumeration-resistant path, a `?` on the lookup is the leak

`recovery_start`, `passkey_recovery_start` and `resend_verification` (`crates/kyomi-ui/src/server_fns/auth.rs`) all promise the same thing in their own doc comments: *"Always returns `Ok(())` to prevent email enumeration."* That promise is about the *observed* outcome, so it survives only if every failure inside the call produces the same outcome as "no such account". A `?` on the user lookup or the token mint does not: it turns a database outage into an `Err`, which the server fn re-raises as `ServerFnError::new("Internal server error")` or via `.into_sfn_core()` — a reply an attacker can tell apart from the silence an unregistered address gets. Nothing about it reads as a leak in review. The `?` is idiomatic, the message is generic, and the enumeration signal is the *shape* of the response rather than its text, so it survives every check that looks at wording.

**Rule:** on a path whose contract is that the caller cannot tell whether the account exists, no internal failure may reach the caller. Match on the lookup instead of `?`-ing it, log the error at `error!` so an outage stays visible to operators, and return the same `None`/`Ok(())` the absent-account branch returns. `lookup_recovery_user` (`crates/kyomi-auth/src/auth_service.rs`) is the shape to copy: it states the contract in its own doc comment (*"callers must not be able to distinguish those, or the endpoint leaks account existence"*) and is pinned by two tests, `lookup_recovery_user_db_error_returns_none_and_logs_error` and `lookup_recovery_user_absent_user_returns_none_without_error_log`. Record the exceptions at the function that upholds the contract, not in the ticket: `passkey_recovery_start_service`'s doc comment names rate limiting as the one deliberate `Err` and notes that the uniform outcome currently also depends on `RecoveryRequestCard` discarding the result — so whoever later surfaces that error knows what they are breaking. This is the enumeration-path exception to `../error-handling/empty-on-failure-must-not-look-like-a-real-result.md`: here a failure *must* look identical to a real result, with the signal preserved only in the logs.

Four sibling functions in one file, fixed one at a time. KYO-285/KYO-286 brought the enumeration-safe `lookup_recovery_user` across from the REST passkey-recovery handler it replaced. KYO-291 (review log `2026-09-02`, `02:05`) then found `recovery_start_service` still `?`-ing both its lookup and its token mint, and mutation-testing the two new regression tests confirmed the leak was real (`Sqlx(PoolClosed)` surfacing as `Err` instead of `Ok(None)`). The same review's trace turned up the identical shape one function above it, in `resend_verification_service` (`crates/kyomi-auth/src/auth_service.rs`), whose caller re-raises the `Err` and so contradicts that endpoint's own "Always returns `Ok(())`" doc comment — filed as KYO-592 rather than fixed inline, and still present on `main`. The reviewer's closing note is why this is a rule and not three tickets: *"Worth watching whether a fourth instance turns up elsewhere in this file — if so, the fix probably belongs in a single shared `lookup_user_enumeration_safe`-style wrapper … rather than another one-off per-function patch."*
